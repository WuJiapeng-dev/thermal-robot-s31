## 一、一句话结论

**主链路代码齐全，但方案 V2 新增的三层定位保障里有两层完全没做，字库是空的，温度换算没有——所以"定位到元件群 ≤8mm"这个核心承诺目前无法验收。**

## 三、六个关键缺口（按对验收指标的影响排序）

### 3.1 定位标定三层保障缺前两层 → 「定位误差 ≤8mm」无法验收

方案第八章验收指标第一条就是「定位误差 ≤8mm」。这个指标依赖：

1. 每次上板的绝对基准（ArUco 或机械限位）— ❌ 无代码
2. 热像与可见光的坐标映射 — ❌ 无代码
3. 标定表记录"热图坐标 ↔ 元件群标签" — ⚠️ 能读表，但无生成流程

**当前实际能力**：只能用「热图坐标 → 矩形区域 → 区域名」的静态查表，一旦机器人相对板面的位置变了（重新摆放、轮子打滑），标定表全部失效。方案第二章第三节开头就写了这个风险："V1 依赖编码器里程复现位姿，但无绝对基准，累积误差会让标定表失效"——**V2 补的三层保障，代码只补了第三层的一半**。

### 3.2 中文字库空白 → 「屏幕可读性」不达标

方案要求 12×12 点阵 500 字子集（约 15 KB）。当前：

- `font12.c` 有 72 个字的 GB2312 编码目录
- 所有 `bitmap` 指针为 `NULL`
- `font12_has_verified_glyphs()` 返回 0

后果：`ui.c` 的顶部区域 `${g_zh}`（中文区域名，如"电源区"）全部显示 `?`。方案第八章验收指标「位号与区域在 0.5m 内可读」**当前不可能通过**。

补法（`开发报告_STM32.md` 第七节有完整 PIL 代码）：24 字节/字、逐行、高字节在前、每行低 4 位无效。**先只灌「电」「源」两字验证位序**，位序错了要全部重来。

### 3.3 温度恒为 -273.0 → 判据与显示双失效

`raw_to_celsius()` 返回 `NAN`，链路里 `t` 和 `dt` 恒为 `-273.0`，STM32 显示 `--`。

后果有两层：

- 显示层：用户看不到温度，只能看到 raw 差值的相对排名。
- 判据层：方案要的是「像素温度 − 板面温度中位数 ≥ 8°C」，代码做的是「raw 计数 − 中位数 ≥ 1500」。这两个不是一回事，1500 也没有任何标定依据。

方案附录「待核实 02」其实预警过这件事：「若仅输出灰度而非辐射温度，判据需按灰度差与黑体参考折算，标定表需记录环境温度」。代码走了灰度差路径，但**没有做黑体折算，也没记录环境温度**。

### 3.4 可见光不取图 → 云端增强与 ArUco 都无从谈起

`app_vision.c` 只做三件事：LEDC 输出 20MHz XCLK、SCCB 探测 `0x30`、读 PID/VER。不配置寄存器、不取帧。

这一项是 3.1 和 3.5 的前置条件：没有可见光图像，既做不了 ArUco 识别，也传不了伪彩图/可见光图给云端。

补充：方案写 OV5640（500 万像素，XCLK 24MHz），代码是 OV2640（200 万，XCLK 20MHz）——这是**提示词选定的型号**，与方案 BOM 不一致，需要确认实物到底是哪颗。

### 3.5 停走式采样未闭环 → 漏检率不可控

方案第六章第二节：0.34m/s 巡航 + 25fps 下每帧位移 13mm，必然漏检，所以改停走式（5mm/点、停 0.5s 采 2 帧）。

当前状态：STM32 侧有 `motion_step_scan()`（移动 + 停留），S31 侧有 `run_scan()`（连采 30 帧做热点分析）。**两者互不知道对方在干什么**：

- S31 不知道车停了没有，只是无脑取 30 帧
- STM32 不知道 S31 采完没有，只是等 0.5s
- 没有「到位 → 通知 S31 开始采 → 采够 2 帧 → 通知 STM32 走下一步」的握手

而且 `ENABLE_MOTION_DRIVE=0`，这套逻辑当前完全不会执行。

### 3.6 云端只有单条上传接口

方案要求上传「伪彩热图 + 可见光图 + Top-3 热点坐标」，云端返回原因分析与维修建议，结果追加到屏幕第二页。

现有两个函数：`app_cloud_upload_hotspot_json(json)` 和 `app_cloud_upload_snapshot(path)`——单条 JSON、单个文件。没有 Top-3 打包，没有响应解析，没有第二页 UI。

由于 `APP_WIFI_ENABLE=0`，这部分当前是死代码。

## 四、本轮修掉的一个真实缺陷

### TB6612 刹车 / 滑行真值表互换（严重，上电即现）

**位置**：`stm32\src\motor.c`（修改前 14~21 行）

**原实现**：

```c
GPIO_WriteBit(MOTOR_AIN1_PORT, MOTOR_AIN1_PIN, left_sign >= 0 ? Bit_SET : Bit_RESET);
GPIO_WriteBit(MOTOR_AIN2_PORT, MOTOR_AIN2_PIN, left_sign <= 0 ? Bit_SET : Bit_RESET);
```

用同一个 `sign` 反推出两根脚，代入方案真值表：

| 调用 | sign | AIN1 | AIN2 | 实际动作 | 方案要求 |
|---|---|---|---|---|---|
| `motor_brake()` | 1 | 1 | 0 | **正转** | 1,1 短路制动 |
| `motor_coast()` | 0 | 1 | 1 | **制动** | 0,0 高阻滑行 |
| 换向前刹车 | 1 | 1 | 0 | **正转** | 1,1 短路制动 |

更糟的是 `motor_brake()` 还把 PWM 设成 `MOTOR_PWM_ARR`（满占空比）——**调用一次刹车，车体全速前冲**。`motion.c` 里有 4 处调用 `motor_brake()`（到达目标、欠压、超时、`motion_stop`），一旦把 `ENABLE_MOTION_DRIVE` 改成 1，第一次定位完成就会冲出去。

**修复**：改为显式方向枚举 `MOTOR_DIR_FORWARD / REVERSE / BRAKE / COAST`，按方案真值表逐脚写死，不再从数值符号推导；新增 `brake_both()` 统一做短路制动；辅助函数全部包进 `#if ENABLE_MOTION_DRIVE`，开关为 0 时不产生未引用警告。

**校验**：括号 21/21、圆括号 96/96、`#if` 与 `#endif` 各 6 处均配对；`motion.c` 的 4 处 `motor_brake()` 与 1 处 `motor_set()` 调用语义现在正确。**但本机无 ARM 工具链，这份修改未经编译验证。**

## 六、如果按「能不能算基本实现」来判

**分两种口径：**

### 口径 A：能不能上电跑通主链路

**基本可以。** S31 侧编译通过（551,280 B，0 warning），初始化链完整，热像→热点→查表→串口→屏显/播报这条路径每一步都有代码，任何一步失败都有明确日志。STM32 侧代码齐全但**从未编译**，第一次编译大概率有一批语法/类型错误要修。

实际会看到的效果：屏显 `UNKNOWN` + `X:.. Y:..` + `T:--`，中文全是 `?`，语音播报有限（字表 70 字）。功能"在"，但不好用。

### 口径 B：能不能通过方案第八章的验收指标

**不能，7 项里只有 2 项有可能通过。**

| 验收指标 | 目标值 | 当前判定 |
|---|---|---|
| 定位误差 | ≤ 8mm | ❌ 无绝对基准、无双目标定，标定表无法对齐实物 |
| 漏检率 | ≤ 5%（ΔT≥10°C） | ❌ 判据是 raw 差值，无法对应 ΔT；采样未闭环 |

| 语音播报延迟 | ≤ 2 秒 | ✅ 设计上满足（队列 + 独立任务），需实测 |
| 断网可用性 | 完全可用 | ✅ **可以**，WiFi 默认关闭，定位与播报不依赖网络 |
| 屏幕可读性 | 0.5m 内可读位号与区域 | ❌ 中文字模空白，区域名全 `?` |

## 七、要补齐的话，建议顺序

按"投入产出比 + 依赖关系"排：

1. **填字模**（半天）：`font12.c` 灌 100~200 字，先验证「电」「源」位序。这一步让屏显从不可用变可用，没有前置依赖。
2. **STM32 首次编译**（1 小时）：装 Keil + SPL，按 `PROJECT_SETUP.md` 建工程，清掉第一批语法错误。这是后面所有 STM32 侧工作的前提。
3. **停走采样握手**（1 天）：给 JSON 加一条 `{"cmd":"capture"}` 下行帧，STM32 到位后发，S31 收到后采 2 帧回 `{"cmd":"done"}`。这是方案第六章第二节的落地。
4. **OV2640 取图**（2~3 天）：先确认 `esp32-camera` 是否支持 `esp32s31`，再接 DVP 驱动。这一步同时解锁 ArUco 和云端上传。
5. **ArUco 位姿**（3~5 天，依赖 4）：识别四角标记、解算单应、写入坐标系原点。
6. **温度标定**（依赖黑体设备）：把 `raw_to_celsius()` 从 NAN 改成真实换算，`HOTSPOT_RAW_DELTA` 才能换成 ΔT≥8°C。

前两项是"让小系统先能看"的最低成本动作；后四项才是方案 V2 的实质内容。
